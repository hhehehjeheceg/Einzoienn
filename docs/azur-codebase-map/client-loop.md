# client-loop

## Architecture
Load order (index.html:60-153): runtime -> three -> world-split -> game-zeropoint -> sim (AZSim) -> build-rules -> meta (AZMeta) -> audio (AZAudio) -> models -> graphics-v48-hero -> vehicles-v74 -> bus-v82 -> graphics-v48-city -> environment -> icons (AZIcons) -> view (AZView) -> render-upgrades -> panels (AZPanels) -> game.js [#78, defines AZGame] -> map-ui (AZMapUI) -> garage (AZGarage) -> social-client (AZSocial) -> client.js [#82, defines AZURHorizons and runs `new Horizons()`] -> horizons-v120..v170 -> graphics-v200-art/world/engine -> horizons-v180 -> polish-v47 -> construction -> map-v65 -> map-poi-v67 -> island-v68 -> characters/weapons/loot/render-toon/skins/anim/emotes -> lobby-v66 -> lobby-v89 -> hud-v67 -> inventory-v67 -> construction-v67 -> ui-v81 -> event-* (event-sequencer first) -> event-end81-* -> zeropoint-v82 -> lobby-v83 -> weapons-v84.

Pattern: game.js is a base class only. client.js subclasses it, then reassigns many of its own prototype methods in a second 'v0.6' block, sometimes wrapping (boot, startGameUI, updateHUD, nearPrompt, onEvent, loop, bind, action) and sometimes fully replacing (renderMenu, lobbyHTML, startMatch, checkResult, queueSave). It then mixes in AZMapUI (overwriting game.js map functions), installs AZSocial wrappers and instantiates the only instance. Later files capture `const previous = P.method` and reassign P.method on window.AZURHorizons.prototype. Since calls resolve through the prototype at call time, the LAST loaded file is the outermost layer. Some layers do not call previous (horizons-v150.js:46 lobbyHTML, inventory-v67.js:119 openInventory, construction.js:138 updateBuildBar, the openEdit/paintEdit replacements), which makes the inner versions dead. Other layers never touch the prototype and instead poll for root.AZUR via setInterval/rAF and decorate the DOM (hud-v67.js, inventory-v67.js:133, polish-v47.js:406, ui-v81.js) or patch AZView.View.prototype (lobby-v89, weapons-v84, horizons-v160/170).

Boot is asynchronous. Game.boot awaits loadProfile and one requestAnimationFrame before it creates the View and world, renders the menu and sets root.AZUR (game.js:155). On slow script fetches the first menu render can happen before later layers load; horizons-v150.js:33-44 works around this by re-clicking the play tab. client.js:1254-1258 replaces view.update with an instance-bound function at boot, which bypasses later AZView.View.prototype.update patches; polish-v47.js:388-406 re-hooks the instance for that reason.

Per frame (game.js:1081 loop, wrapped by event-sequencer, construction, graphics-v200-engine, horizons-v120 (gamepad), client): input -> world.command, fixed 60 Hz world.step, AZEvent.beforeView, view.update(world, player, dt, opts), audio.update, and every 0.13 s updateHUD (rewrites many innerHTMLs) plus minimap drawing. UI events use event delegation: any element with data-act/data-id triggers this.action(act, id, el) through the click listener in client.js:427-434, which walks the action wrapper chain down to game.js:386.

The text is entirely French and uses original names (AZUR, Île Corail, Alizé bus, Écus de corail).

## How to modify safely
1. Do not edit the dead methods; edits there change nothing at runtime. In game.js these are queueSave, renderMenu, lobbyHTML, startMatch, connect, startGameUI, bind, fireOnce, updateHUD, checkResult, togglePause, openInventory, buildMapTexture, drawMap, openMap, drawFullMap. In client.js they are class renderMenu (121), class lobbyHTML (152), class startMatch (711) and prototype lobbyHTML (1344, replaced by horizons-v150.js:46). The live HUD is client.js:822 updateHUD + 749 startGameUI. The live menu shell is client.js:1315. The live lobby body is horizons-v150.js:46. The live match start is client.js:1480. The live results screen is client.js:1386/1519.

2. The preferred way to add a big overhaul is a NEW late-loaded layer (for example fortnite-v92.js plus a .css) added to index.html after weapons-v84.js. Use the established pattern: `const H=root.AZURHorizons, P=H.prototype; const prev=P.updateHUD; P.updateHUD=function(){prev.call(this); /* decorate */};`. Because it loads last it becomes the outermost wrapper, and it can fully replace methods when needed (lobbyHTML, buildResultsHTML, startGameUI). Load CSS last (after lobby-v83.css) so it wins the cascade over the roughly 30 stylesheets.

3. Keep the DOM IDs that later layers read: #remaining, #kills, #compass, #phase-title, #phase-detail, #minimap, #storm-timer, #region-name, #storm-warning, #scope, #crosshair, #damage-confirm, #elimination-confirm, #flight-speed, #emote-status, #interaction, #feed, #health-block, #shield-bar, #health-bar, #shield-value, #health-value, #ammo, #use-progress/#use-label/#use-meter, #materials, #slots, #build-bar, #build-status, #world-edit, #joy, #joy-nub, #touch-fire, #touch-utility, #fps, .hud, .touch-controls, .game-toolbar, .game-hint, .v7-lobby-card (polled by horizons-v150), .play-btn, [data-act=choose-mode]. hud-v67.js, inventory-v67.js, horizons-v120/130/140/170/180, construction.js and event-mode.js query these, and removing them silently breaks those layers.

4. updateHUD runs every 0.13 s and resets innerHTML on #ammo, #materials, #feed and #compass (only when the heading changes). Decorations added inside those nodes are wiped each tick, so put new widgets in sibling nodes created once (as client.js:1514-1515 does for #revive-progress) or cache-compare before writing.

5. Changing durations needs to happen in several places. Pre-game 10 s is set in sim.js:415 and again in the client.js:853 countdown math. The lobby prep 3 s is at client.js:1359. The bus 38 s is in sim.js MAP.transport. A Fortnite-like 60 s warm-up with 'BUS LAUNCHING IN N' needs both sim and HUD changes. Phase strings are at client.js:851-880.

6. Actions: add new data-act verbs by wrapping P.action and returning early for your verb, falling through with prev.call(this, act, id, el). Remember 'play' is captured at client.js:1429 (local prep), 'emote' at 1422 (picker) and build-mode/build-type/material by construction.js:112. Keys: extend DEFAULT_BINDS and BIND_NAMES and the act map at client.js:586-592. These constants are closure-private, so a later layer must patch this.keybinds at runtime (for example after boot) or add its own keydown listener. inventory-v67 uses a capture-phase keydown with stopImmediatePropagation for Tab, I and Escape.

7. Map: patch Horizons.prototype.buildMapTexture/drawMap (the prototype copies), not root.AZMapUI, which no longer has any effect after client.js:1599. Call this.buildMapTexture() again after patching, because boot already built the texture.

8. View hooks: client.js:1254-1258 binds view.update on the instance at boot. To hook rendering, either patch AZView.View.prototype methods that update() calls internally, or re-wrap the instance like polish-v47.js:388-406 does.

9. Instance access: window.AZUR exists only after async boot finishes (game.js:155). New code that needs the instance must poll or hook P.boot (wrap it with `await prev.call(this)` and then act).

10. Saves: the profile is normalized by AZMeta.normalize. New persistent fields must survive normalize (check meta.js) or they will be dropped. Creative blueprints use localStorage 'azur-creative-v2'.

11. Version strings get regex-rewritten by horizons-v160/180 (/1\.[3-7]/ -> 1.8). Avoid such literals in new text, or expect them to change.

12. Keep French copy and original names (no Fortnite trademarks). Mirror Fortnite's layout and behaviour, not its branding.

13. After any change, launch index.html, take a screenshot of each screen (lobby, bus, skydive, in-game HUD, build, results) and save it under production/qa/evidence/, as the project's run-and-observe rule requires.
