# map-island

## Architecture
Load order (index.html:62-160) for these files and their neighbours: three.min.js → world-split → game-zeropoint → sim → build-rules → meta → audio → models (base AZArt) → graphics-v48-hero (installs a get/set accessor chain on AZArt.avatar and AZArt.weapon) → vehicles-v74 → bus-v82 → graphics-v48-city → environment (AZEnvironment) → icons → view (AZView) → render-upgrades → panels → game (AZGame) → map-ui (AZMapUI) → garage → social-client → client (class Horizons; Object.assign(Horizons.prototype, AZMapUI) at :1599; root.AZURHorizons; new Horizons() at :1603) → horizons-v120…v170 → graphics-v200-art → graphics-v200-world → graphics-v200-engine → horizons-v180 → polish-v47 → construction → map-v65 → map-poi-v67 → island-v68 → characters/weapons/skins/anim/emotes/lobby-v66/lobby-v89/hud/inventory/construction-v67/ui-v81 → event-* → event-end81-* → zeropoint-v82 → lobby-v83 → weapons-v84 → ch1-view/hud/flow/lobby-v92. The four ch1 files are currently empty IIFE stubs that load last.

Runtime: `new Horizons()` runs synchronously when client.js loads, but boot() is async. The View, and with it Environment, view.aircraft (A.aircraft) and makeMenu, is constructed only at game.js:135, after `await loadProfile()` and a requestAnimationFrame. By then every script, including the ch1-*-v92 stubs, has loaded, so all prototype and AZArt overrides are in place when the objects are built. Environment presentation is built lazily on the first E.update call: installWorldV2, then ensureV65MapDetails, ensurePoiDecor and the v68 biomes.

Final AZEnvironment.Environment.prototype.update chain, outermost first:
1. island-v68 (calls previous first, then installs and animates)
2. map-poi-v67 (pre)
3. map-v65 (pre)
4. horizons-v180 v21 world FX (post)
5. horizons-v180 v18 landmarks (pre)
6. graphics-v200-world (base REPLACEMENT)

environment.js:495 and the horizons-v160:184 wrapper are dropped. view.js:740 calls it with (dt, playerPos, day, quality).

AZView.View.prototype.drawMenu chain: lobby-v83 → lobby-v89 → lobby-v66 → graphics-v200-world (base). The render-upgrades and horizons-v160 drawMenu versions are dropped. makeMenu and setClassicLobbyMode are owned by lobby-v66, so the v200 hangar scene is dead code.

AZView.View.prototype.update is a long wrapper chain (render-upgrades, polish-v47, v200-world, v200-engine, horizons-v170, loot-v67, characters-v67, construction-v67, zeropoint-v82, weapons-v84 …). zeropoint-v82 is one of the last wrappers.

AZArt.avatar chain (through the v48-hero accessor; each later layer's captured 'base' is the accessor, which descends one level): skins-v89 → skins-v81 → render-toon → graphics-v200-art avatar(). The final group is passed through the hero material apply().

AZArt.weapon chain: weapons-v71 → weapons-v67 (v200 weapon() is unreachable through the chain).

Other overrides:
- AZArt.aircraft is replaced by bus-v82.
- AZArt.vehicleModel is wrapped by vehicles-v74.
- AZArt.objectModel is wrapped by graphics-v200-world for tree, rock and house.
- AZSim.World.prototype._createMap is wrapped by map-poi-v67.

AZMapUI is a mixin copied at client.js load, so map-poi-v67's later edit of AZMapUI.buildMapTexture does not reach Horizons.prototype: POI markers never draw on the map.

Terrain colour: graphics-v200-world recolourTerrain runs first (inside installWorldV2), then island-v68 recolour overwrites the same 'color' attribute in the same first frame. Only zoneColor (island-v68.js:32) is visible.

All my files guard on their dependencies (`if (!T || !S || …) return;`), so a missing dependency silently disables the layer.

Notable mismatches relative to the Chapter 1 reference:
- no rivers
- the lake is in the south, not the centre
- the bus palette and design are original
- the glider is a propeller hang-glider and there is no umbrella
- the avatar is a big-head cartoon rather than the realistic soldier
- the vehicles are modern cars and a buggy
- the full-map labels are boxed
- the minimap name is the nearest town

## How to modify safely
1. Put new behaviour in a NEW late-loading layer, preferably the existing empty stubs ch1-view-v92.js, ch1-hud-v92.js, ch1-flow-v92.js and ch1-lobby-v92.js, which load last (index.html:157-160). Do not edit the middle of old files. Inside a stub, always wrap rather than replace: `const prev = X.fn; X.fn = function(...a){ const r = prev.apply(this, a); /* add */ return r; }`. Replacing without calling prev silently discards every earlier wrapper; graphics-v200-world did exactly that to E.update and drawMenu.

2. Environment and world art: hook AZEnvironment.Environment.prototype.update(dt, focus, day, quality) as the other layers do.
   - Build lazily on the first call: `if (!this.myLayer) {...; this.root.add(group)}`.
   - Cull by distance to `focus`, and respect `quality` ('low'|'medium'|'high'|'ultra') and root.AZUR.view.adaptiveDetail.
   - To hide an older layer, set .visible=false on env.worldV2.*, env.v65MapDetails, env.v66Pois.group or env.v68Island.group (or on its children) after calling prev.
   - To change terrain colours, edit island-v68 zoneColor or recolour after island-v68 (in a later wrapper, after prev on the first frame). Editing graphics-v200-world terrainColour has no visible effect.

3. Map, minimap and HUD map: patch root.AZURHorizons.prototype.drawMap, buildMapTexture or openMap. Do NOT patch root.AZMapUI after client.js, because that is ignored. If you change buildMapTexture, call `root.AZUR.buildMapTexture()` again after boot (it runs once at game.js:148). drawMap(c, full) is called every HUD tick for '#minimap' (240px) and from drawFullMap for '#full-map' (660px). To show Fortnite-style POI names, iterate S.pois and S.regions in a drawMap wrapper with white text and a dark stroke (no boxes). To show the minimap POI name, patch the client.js:908-911 logic (region-name) to consider S.pois.

4. Sim-side map content (POIs, chests, objects): only wrap AZSim.World.prototype._createMap after calling previous. Use this._object(type,x,z,w,h,material,yaw) and this.rng, never Math.random, so the result stays deterministic for LAN and replays. Object ids are sequential, so inserting objects changes later ids. Keep additions at the end, wrapped in try/catch as map-poi-v67 does. Moving POIs requires keeping the map-poi decor positions (taken from the same POIS array via P(id)) and the island-v68 lookups ('jade', 'canyon') consistent. A central lake would need sim height and water changes (sim.js LAKE and isWater, :197), not just art.

5. Characters: assigning `A.avatar = fn` does NOT replace; graphics-v48-hero's accessor pushes onto a chain. Write `const base = A.avatar; A.avatar = function(eq, d){ const g = base.apply(this, arguments); /* hide or add parts */ return g; }` and re-publish `root.AZView.avatar = A.avatar`. Keep the v200 avatar userData contract (limbs order [hipL,shoulderL,hipR,shoulderR], knees, elbows, torso, head, gun, tool, glider, handTargets, restLimbPositions, avatarScale, equipment) because animation, IK, skins and the event code read it. skins-v89 already hides the old parts and adds its own (u.v89hero), so a new default-soldier look should follow its pattern (hideOldDeep plus parts on u.torso, head and limbs).

6. Weapons: A.weapon goes through the same accessor. Write a wrapper that keeps the userData {weapon, grip, supportGrip, muzzle, barrelAxis, presentation}, because render-upgrades uses these for IK, recoil and muzzle flashes. Rarity colour is applied by weapons-v67 and characters-v67, so hook there or after.

7. Bus and glider:
   - Replace A.aircraft in a late file but keep its userData keys: balloon, body, thrusters, turbines, cabinPanes, navLights, headlights, energyCore, interior, burner, cameraTarget, cameraRadius, cameraRadiusPortrait. view.js:949-970, polish-v47 ensureBus (which attaches plumes, beams and a strobe once per aircraft instance) and lobby-v66:142 all depend on them. Empty arrays are acceptable for parts you drop.
   - The model is scaled ×2.7 and flies at y≈1500.
   - The glider lives inside the avatar (u.glider with userData.handles). Replace its children but keep the group and its handles.

8. Vehicles: add builders by wrapping A.vehicleModel per v.type, and keep userData.wheels, steeringWheels and seat. New types (for example 'cart', 'atk', 'quad', 'plane') also need sim support (sim.js:326 spawn list, :735 driving, :990 crafting).

9. Lobby: drawMenu's base is graphics-v200-world.js:465, under lobby-v66, v89 and v83. To restyle the stage, wrap V.drawMenu after lobby-v83 and toggle this.v2Lobby.root children, or add a new group to this.menuScene. Keep the v2Lobby keys {waterUniforms, ring, ring2, beam, cloud, bulbs, motes, sun, rim}, because the v200 drawMenu dereferences them every frame and throws if one is missing. Camera framing is the hard-coded block at lines 488-494; override it after prev by repositioning this.menuCamera and re-rendering, or by replacing the whole function carefully.

10. FX: reuse A.fx.* (pooled and capped) instead of allocating per event. view.js already routes shot, hit, explosion, elimination, harvest, land, deploy, build and loot events to it.

11. Zero Point: it depends on AZEnd81 from the event-end81 files. If the event files change or are removed, zeropoint-v82 silently stops. It hides any origin SphereGeometry of radius 18 or 28 that uses MeshBasicMaterial, so avoid those exact radii at the origin.

12. Cache busting: every script tag uses ?v=92. Bump it on all tags (and on any new file) when shipping, or browsers may mix old and new layers. Test on 'low' quality and on mobile too: island-v68 lowQ and FX.setMobile change counts and code paths.

## Files
### map-v65.js
Instanced decoration layer on the island, visual only with no collisions: wind-swaying grass tufts, lumpy bushes, mushrooms in the forest, fallen logs, hay bales around the farm region, beach parasols and towels, and offshore boats and buoys that bob on the swell.
