# ui-meta-lobby

## Architecture
Load order (index.html) for my files: meta.js(68), then audio.js(69), icons.js(76), panels.js(79), garage.js(82), music-v69.js(104), lobby-v66.js(111), lobby-v89.js(112), ui-v81.js(116), lobby-v83.js(154). The v92 'Chapitre 1' files ch1-view-v92.js, ch1-hud-v92.js, ch1-flow-v92.js and ch1-lobby-v92.js (157-160) and their CSS are empty IIFE stubs that load last; they are the intended hook points. Everything is IIFE plus window globals. meta.js and panels.js are UMD, so they also export under Node, which is useful for unit tests.

Menu 3D render chain. view.js:526 holds the base drawMenu, and render-upgrades.js:641 wraps it. graphics-v200-world.js:465 then REPLACES drawMenu (avatar, team slots, ring/cloud animation, camera framing, renderOneThumbnail). lobby-v66 wraps that, lobby-v89 wraps lobby-v66, and lobby-v83 wraps lobby-v89; lobby-v83 is the outermost wrapper today. Execution order per frame:
1. v83 calls prev.
2. v89 runs upgrade() once, animates, then calls prev.
3. v66 lazily runs makeLobby if v2Lobby.v66 is missing, then calls prev.
4. v200 draws the avatar, places the camera and calls renderer.render.
5. v66 animates its objects (this lands after the render call, so the changes show next frame).
6. v83 upgrades and animates the rift.

makeMenu: graphics-v200-world (hangar) was wrapped by graphics-v200-engine (light tweak), and lobby-v66 then REPLACES it. setClassicLobbyMode: graphics-v200-world, wrapped by horizons-v180, then REPLACED by lobby-v66.

Lobby HTML chain: game.js lobbyHTML, then client.js:1344 Horizons.prototype.lobbyHTML, then wrappers in horizons-v120, v130 and v140. horizons-v150 REPLACES it with the 'classic-progress' left column and level shield. horizons-v180 appends a rail. lobby-v83 appends the event card.

Panels: client.js renderMenu (line ~1323) calls AZPanels.render(tab, game) except for group, settings and help. ui-v81 wraps render for locker and shop. After render, client.js queuePanelThumbnails finds `.exp-cosmetic` elements with `[data-act=preview][data-id]` and `.exp-card-art`, and prepends 3D canvas thumbnails.

Audio: game.js:100 creates `new AZAudio()`. game.js:1135 calls audio.update(...) each frame and game.js:1151 calls audio.event(e,p) for each sim event. Prototype patches: weapons-sfx-v69 replaces report and wraps event; music-v69 wraps update and runs its own 200 ms scheduler.

The lobby scene accumulates about 11 lights: v66 adds hemi, sun, rim and spot; v89 adds 4 directional lights; v83 adds spot, directional and point. It also stacks two podiums (v66 cylinder plus torus, v89 textured disc plus band). Every patch guards on dependencies (`if (!T || !V) return`) and silently no-ops when they are missing. Errors are console-logged with the tags '[AZUR salon v89]', '[AZUR lobby83]' and '[AZUR ui81]'.

Boot timing: game.boot() is async (await loadProfile, then a requestAnimationFrame). AZView.View is constructed and root.AZUR assigned only after that. This is why the lobby patches upgrade lazily inside drawMenu instead of at load time.

## How to modify safely
1. Put new code in the late stub files. For lobby changes that is ch1-lobby-v92.js plus ch1-lobby-v92.css (loaded after lobby-v83 and every other patch). Avoid editing the old layers; wrap them from the stub, matching the pattern used everywhere (`var prev = V.drawMenu; V.drawMenu = function(){ ... prev.apply(this, arguments) ... }`). Guard with try/catch, log a tag, and keep an idempotence flag such as `view.v2Lobby.ch1` or `M.normalize.__ch1`.

2. Replacing the lobby 3D scene is a trap. lobby-v66's drawMenu wrapper rebuilds its whole scene every frame whenever `this.v2Lobby.v66` is missing. v89 and v83 key off `v2Lobby.v66` and `v2Lobby.v83`. graphics-v200-world's drawMenu writes `l.ring.rotation`, `l.ring2`, `l.beam.material`, `l.cloud.rotation` and `l.waterUniforms.time` with no null checks. Two clean options:
   (a) Keep v2Lobby and hide or replace children. Set `v2Lobby.root.visible=false` (but setClassicLobbyMode sets it back to true every frame), or better, toggle the visibility of individual meshes and add your own Group. Remove the extra v89 and v83 lights with scene.remove.
   (b) REPLACE V.drawMenu outright in ch1-lobby-v92.js without calling prev. Re-implement the avatar, team and camera logic by copying graphics-v200-world.js:465-496: A.avatar(eq), this.animateAvatar, this.setMenuTeam, menuRotation, setViewOffset and renderOneThumbnail. Also replace V.makeMenu and V.setClassicLobbyMode. Option (b) avoids the stacked podiums and about 11 lights.

3. Squad-mate placement (Fortnite-style side-by-side platforms) and camera framing live in graphics-v200-world.js:477-494, not in the lobby-v* files.

4. Profile and economy changes go through AZMeta.
   - Add cosmetics with `AZMeta.catalog.push(...)`. It is the same array as the closure `catalog`, so byId, purchase and equip see the new items.
   - Change the default skin or currency name by wrapping AZMeta.normalize with a NEW one-time migration flag, as skins-v81 and skins-v89 do. Otherwise kai089 or sentinelle081 will re-equip their skins on fresh profiles.
   - Internal meta functions (purchase, equip, claim, level) use the private normalize and will not see your wrapper.
   - `rewards` and `quests` are closure arrays shared with AZMeta.rewards and AZMeta.quests. Mutate them in place (splice or push); never reassign.
   - Adding a green 'Uncommon' rarity means changing the panels.js `rarity` map (line 7), the ui-v81.js `RAR` map (line 16) and the ui-v81.css `--r-*` variables and `.r-*` classes together. Existing items use 1-4.

5. Menu pages: wrap AZPanels.render again, as ui-v81 does. Keep the existing data-act names (equip, purchase, claim, preview, locker-filter, shop-filter, tab, and so on) because client.js handles them. Keep `.exp-cosmetic`, `[data-act=preview][data-id]` and `.exp-card-art` if you want the 3D thumbnails. Tabs 'group', 'settings' and 'help' are intercepted in client.js renderMenu before AZPanels.

6. Lobby HTML (PLAY button, mode card, level panel) is built by the Horizons.prototype.lobbyHTML chain, with horizons-v150 as the base replacement. Wrap or replace it in ch1-lobby-v92.js. If you replace it, re-append lobby-v83's event card (or drop it on purpose). The click delegation for [data-v83-event] is a document-level capture listener and keeps working.

7. CSS specificity: lobby-v83.css and earlier sheets use `html body[data-screen=...][data-tab=...] ... !important`. New CSS in ch1-*.css, which loads last, needs equal specificity plus !important to win.

8. Audio: add methods on AZAudio.prototype and wrap `event` (e.g. new e.type values for chest hum, bus horn, storm warnings). Keep weapons-sfx-v69 in mind: it replaced `report` and wraps `event` for reload. music-v69 zeroes settings.music while the legacy update runs, so new music should be scheduled outside A.update. Either add songs inside music-v69.js (SONGS and wanted() are private) or write a separate scheduler. If you write a separate one, make it return early when the v69 one is active, to avoid double music. Storm cues depend on sim phase text matching /^contraction/ and /^tempête/; keep those strings or update audio.js:159-162.

9. Icons: add missing names to the `paths` map in icons.js, or wrap AZIcons.icon. 'chevron' is already referenced by client.js. For distinct consumable and ammo icons, wrap AZIcons.inventory and switch on it.kind or it.item, then fall back to the original. Character portraits need assets/{model||id}.webp; 'scout' is missing.

10. Timing: the View is constructed asynchronously after all scripts load, but code that touches AZUR or view at load time must tolerate both orders (see graphics-v200-world.js:516-517 `if (root.AZUR?.view) ...`). Prefer lazy initialisation inside drawMenu or update.

11. Performance: ui-v81 and music-v69 run permanent setIntervals. The lobby already holds about 1000 instanced objects plus 11 lights. When adding scenes, dispose old geometries with view.disposeTree and avoid more always-on lights.

12. Testing: meta.js and panels.js load under Node (module.exports), so unit tests can require them directly for economy and pass changes without a browser.
